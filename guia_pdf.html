RF01: Control de Acceso y Autenticación de Usuarios Seguridad & Login
Propósito: Permite ingresar al sistema validando credenciales cifradas con Bcrypt, protegiendo contra bots mediante CAPTCHA, verificando estado activo de usuario, persona y rol, y renovando la sesión para evitar ataques.
AuthController.php (Líneas 37-71)
Líneas 39-47: Validación de Formulario Web
$request->validate(['usuario' => 'required', 'password' => 'required', 'captcha' => 'required']);
📌 ¿Qué hace? Comprueba que ningún campo venga vacío antes de enviar consultas a la base de datos.
🎤 Dilo al jurado: "Aplicamos validación de entrada en el controlador para detener peticiones malformadas o vacías antes de tocar el modelo de datos."
Línea 50: Validación del CAPTCHA Anti-Bot
if (!$this->authService->validateCaptcha($request->input('captcha'))) { ... }
📌 ¿Qué hace? Compara las letras escritas por el usuario contra el código secreto guardado en la sesión.
🎤 Dilo al jurado: "Cumplimos el CU01 implementando un CAPTCHA matemático/gráfico que neutraliza ataques automatizados de fuerza bruta y diccionarios."
Línea 63: Regeneración de Sesión
$request->session()->regenerate();
📌 ¿Qué hace? Borra el código de cookie anterior y emite uno completamente nuevo en el navegador.
🎤 Dilo al jurado: "Es una medida de seguridad OWASP contra ataques de fijación de sesión (Session Fixation) para que nadie suplante la identidad del usuario."
AuthService.php (Líneas 56-89)
Líneas 58-60: Búsqueda con Eager Loading
$usuario = Usuario::with(['persona', 'rol'])->where('nombre_usuario', trim($username))->first();
📌 ¿Qué hace? Busca al usuario en PostgreSQL y carga de un solo viaje a la persona física y a su rol.
🎤 Dilo al jurado: "Usamos Eager Loading con with() para resolver el problema de consultas N+1, trayendo la relación persona y rol en una sola ejecución optimizada."
Líneas 66-76: Verificación de Estados Activos
if (!$usuario->activo || !$usuario->persona->activo || !$usuario->rol->activo) { throw new Exception(...); }
📌 ¿Qué hace? Triple candado: la cuenta debe estar activa, el trabajador no debe estar cesado, y el rol no debe estar inhabilitado.
🎤 Dilo al jurado: "Validamos la integridad humana y operativa: si un trabajador es dado de baja en RRHH, su acceso se revoca de inmediato aunque su cuenta esté creada."
Línea 78: Verificación Criptográfica
if (!$this->passwordService->verify($password, $usuario->password_hash)) { ... }
📌 ¿Qué hace? Compara la clave ingresada contra el hash seguro Bcrypt almacenado en la base de datos.
🎤 Dilo al jurado: "Las contraseñas nunca se guardan legibles. Se verifican mediante funciones hash unidireccionales saladas con Bcrypt."
❓ Pregunta de Jurado: ¿Por qué no arrojan 'Usuario no existe' y en su lugar dicen 'Usuario o contraseña incorrectos'?
💡 Respuesta: Por directriz de seguridad informática OWASP: no revelar si un nombre de usuario existe o no previene la enumeración de usuarios por atacantes externos.
RF02: Gestión de Personal y Cuentas de Usuario Usuarios & Roles
Propósito: Permite a Gerencia crear trabajadores (GERENTE, COUNTER, CONTABILIDAD). Usa transacciones atómicas para no dejar registros huérfanos entre persona y usuario, y registra auditoría RN16.
UsuarioController.php (Líneas 70-134)
Líneas 79-81: Validación de Roles y Longitud de Contraseña
'id_rol' => Rule::exists('rol')->whereIn('nombre', ROLES_PERSONAL), 'password' => 'min:8'
📌 ¿Qué hace? Solo permite asignar roles administrativos y exige contraseñas de al menos 8 caracteres.
🎤 Dilo al jurado: "Restringimos a nivel de regla de validación que por esta vía solo se cree personal administrativo autorizado, garantizando políticas de contraseñas robustas."
Línea 85: Transacción Atómica (ACID)
DB::transaction(function () use ($validated) { ... });
📌 ¿Qué hace? Si la persona se crea pero falla la creación del usuario o la auditoría, TODO se revierte (Rollback).
🎤 Dilo al jurado: "Aplicamos DB::transaction() para asegurar atomicidad e integridad referencial en la base de datos PostgreSQL: o se guarda todo correctamente o no se guarda nada."
Línea 96: Reutilización de Personas
$persona = Persona::firstOrCreate(['tipo_documento' => ..., 'numero_documento' => ...], [...]);
📌 ¿Qué hace? Si el DNI ya existía en la base de datos lo reutiliza; si no existía, crea el registro.
🎤 Dilo al jurado: "Usamos firstOrCreate para normalizar personas naturales y evitar duplicidad de entidades físicas en la base de datos."
Línea 120: Bitácora de Auditoría (RN16)
Auditoria::registrar(Auth::id(), 'CREAR_USUARIO', 'usuario', $usuario->id_usuario, ...);
📌 ¿Qué hace? Guarda qué usuario ejecutó la acción, la fecha y la descripción, pero NUNCA guarda contraseñas.
🎤 Dilo al jurado: "Cumplimos la regla RN16 de trazabilidad corporativa: toda creación o cambio de perfil queda registrado con responsable y hora exacta."
❓ Pregunta de Jurado: ¿Quién tiene autorización para cambiar la contraseña de otro usuario?
💡 Respuesta: Exclusivamente el rol GERENTE mediante el CU05. La clave anterior se invalida inmediatamente y el cambio queda registrado en la auditoría sin exponer el texto del secreto.
RF03: Panel de Control y Resumen Operativo KPIs & Analítica
Propósito: Ofrece a Gerencia y Counter la información del día en tiempo real: reservas de hoy, salidas de tours, pagos pendientes por validar, dinero neto recaudado y próximas salidas con vista SQL.
DashboardController.php (Líneas 10-53)
Líneas 12-14: Desvío de Clientes
if (auth()->user()->tieneRol('CLIENTE')) { return redirect()->route('portal.dashboard'); }
📌 ¿Qué hace? Si un cliente entra al sistema, no ve finanzas ni salidas de la agencia, sino su propio panel de pasajero.
🎤 Dilo al jurado: "Control de acceso basado en roles (RBAC): segregamos la vista gerencial/operativa del portal de autoservicio del cliente."
Líneas 33-35: Recaudación Neta Real
$totalRecaudado = DB::table('pago')->where('estado', 'VALIDADO')->sum(DB::raw('monto_base - monto_base_devuelto'));
📌 ¿Qué hace? Suma los pagos reales cobrados y descuenta los reembolsos por cancelaciones.
🎤 Dilo al jurado: "Calculamos el saldo neto real en caja restando las devoluciones aprobadas, ofreciendo información financiera fidedigna."
Líneas 38-44: Consulta a Vista SQL Especializada
DB::table('vw_disponibilidad_salida')->whereDate('fecha', '>=', $hoy)->limit(5)->get();
📌 ¿Qué hace? Pide a PostgreSQL las próximas salidas usando la vista que ya calculó cupos ocupados y disponibles.
🎤 Dilo al jurado: "Aprovechamos las vistas en PostgreSQL (vw_disponibilidad_salida) para delegar los cálculos pesados de cupos al motor relacional, optimizando la respuesta web."
❓ Pregunta de Jurado: ¿Por qué separan pagos pendientes de pagos validados en el Dashboard?
💡 Respuesta: Porque los pagos pendientes son transferencias o vouchers subidos por los clientes que requieren conciliación contable. Sirve como bandeja de trabajo pendiente para Contabilidad.
RF04: Gestión de Clientes y Ficha Integral Clientes & RN02
Propósito: Registra clientes (directos o corporativos), valida documentos legales peruanos (DNI 8 dígitos, RUC 11), evita duplicados (Regla RN02) y consulta cotizaciones y reservas asociadas.
ClienteService.php (Líneas 99-139)
Línea 102: Validación Oficial de Documento
$this->validador->validar($datosPersona);
📌 ¿Qué hace? Valida que un DNI tenga exactamente 8 dígitos y que un RUC tenga 11 dígitos numéricos válidos.
🎤 Dilo al jurado: "Garantizamos calidad de datos desde el origen aplicando validadores específicos de identificación peruana."
Líneas 114-117: Regla de Negocio RN02 (Unicidad de Cliente)
if ($personaExistente && Cliente::where('id_persona', $personaExistente->id_persona)->exists()) { throw new InvalidArgumentException('La persona ya está registrada como cliente.'); }
📌 ¿Qué hace? Impide que una persona sea registrada dos veces como cliente con el mismo DNI.
🎤 Dilo al jurado: "Implementamos rigurosamente la regla RN02 del SRS: una persona natural solo puede poseer un expediente de cliente en la base de datos."
Línea 119: Promoción de Pasajero a Cliente
$persona = $this->obtenerOCrearPersona($datosPersona);
📌 ¿Qué hace? Si la persona ya viajó antes como acompañante, se reutiliza su registro de persona sin duplicarlo.
🎤 Dilo al jurado: "El sistema normaliza la entidad Persona: un acompañante de viaje puede ser promovido a Cliente titular manteniendo su historial sin redundancia de datos."
RF05: Catálogo de Destinos Turísticos Catálogo & Soft-State
Propósito: Gestiona los destinos de la agencia en Tacna (Miculla, Calientes, Tarata, etc.). Controla altitudes (msnm), recomendaciones, y aplica borrado lógico (activo = false) para proteger reservas pasadas.
CatalogoService.php (Líneas 37-64 y 96-100)
Líneas 44-46: Control de Nombres Duplicados
if (Destino::where('nombre', $nombre)->exists()) { throw new InvalidArgumentException('Ya existe un destino con ese nombre.'); }
📌 ¿Qué hace? Evita registrar dos destinos con el mismo nombre para que no haya confusiones al cotizar.
🎤 Dilo al jurado: "Validamos la unicidad del nombre del destino a nivel de servicio y base de datos para asegurar un catálogo consistente."
Líneas 96-100: Borrado Lógico (Soft State)
$destino->activo = $activo; $destino->save();
📌 ¿Qué hace? En lugar de usar DELETE de SQL, solo cambia el campo activo a false.
🎤 Dilo al jurado: "Aplicamos Borrado Lógico (Soft Delete): no usamos DELETE en SQL para no violar claves foráneas ni destruir el histórico contable y turístico de tours ya realizados."
❓ Pregunta de Jurado: ¿Qué pasa con las cotizaciones antiguas si un destino se desactiva?
💡 Respuesta: Siguen funcionando y mostrando la información completa porque el registro sigue existiendo en PostgreSQL. Simplemente el destino deja de aparecer en los combos desplegables para nuevas ventas.
